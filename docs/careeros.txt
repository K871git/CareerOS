1. WHAT IS CAREEROS?
--------------------------------------------------------------------------------

CareerOS is a modern engineering growth platform for students and software
engineers. Official tagline: "The Path for NextGen Engineers!"

It is NOT:
  - An interview prep / quiz website
  - An online course marketplace
  - An AI chatbot landing page
  - A generic SaaS dashboard

It IS: A platform for building engineering judgment through five pillars:
  A. Understand   — Teach concepts deeply (what, why, how, trade-offs, examples)
  B. Practice     — MCQs, scenario-based, debugging, code review problems
  C. Measure      — Topic/subject performance, weak areas, improvement over time
  D. Explain      — Ollama AI explains answers, gives hints, simplifies concepts
  E. Evolve       — AI-assisted development, modern engineering practices

Target users:
  - Students / beginners learning programming and SE fundamentals
  - Junior devs (0–2y) strengthening foundations
  - Mid-level engineers (2–5y) closing skill gaps

Core belief: AI can assist with implementation, but engineering understanding,
verification, responsibility, and judgment remain essential.

Developer: Kishor — 2+ years full-stack at Biz Secure Labs (Net Protector
Antivirus). Building CareerOS as both a real product AND a learning journey.
Mentorship style expected: explain WHY before coding, explain trade-offs.

API convention: /api/v1/ prefix
Standard response shape: { success: bool, message: string, data: any }
Namespace: App\Http\Controllers\Api\V1 (PSR-4 dir: API/V1)

3. AUTHENTICATION
--------------------------------------------------------------------------------

Email/password:
  - Register, Login, Logout, /me (Sanctum Bearer)
  - OTP send + verify (hashed with bcrypt, 2-min cooldown, 5-min expiry)
  - Password reset (Laravel Password broker → React /reset-password?token=&email=)

Google OAuth:
  - Socialite stateless flow
  - SocialAuthController handles callback
  - Account linking: if email exists → link google_id, if not → create user
  - Frontend: /auth/callback page catches token from redirect

Auth config:
  - Sanctum token expiry: env('SANCTUM_EXPIRATION', 10080) = 7 days
  - OTP: hashed (bcrypt), stored as varchar(255), not plain text
  - Password reset: always returns success (prevents email enumeration)

User model fields:
  - id, name, email, password (nullable for Google-only accounts)
  - google_id, avatar, email_verified_at, timestamps

5. COMPLETED MODULES
--------------------------------------------------------------------------------

5.1 Learning System
  - Hierarchy: LearningTrack → Subject → Topic → Lesson
  - Subjects have 5 levels, each with topics + lessons + 10-question exam
  - Pass threshold: 80% (8/10 correct)
  - LevelCompletion: unique per user+subject+level, tracks score + passed
  - Cache: level.status.{userId}.{subjectId} (5 min), busted on exam submit
  - Options shuffled on return (correct answer not always position A)

5.2 Theory Level System (MCQ-based)
  - 8 areas: languages, frameworks, networking, operating-systems, databases,
             system-design, sdlc, data-structures
  - 3 levels per area with progressive thresholds (L1: 8/10, L2: 9/10, L3: 10/10)
  - TheoryCompletion: unique(user_id, theory_area, level)
  - Unlocking: must pass L1 before L2, etc.
  - Only 'languages' area is currently ACTIVE (config/theory.php ACTIVE_AREAS)
  - Anti-stuffing: exam questions validated to belong to correct area+level
  - Cache busted on submit: progress.overview.{userId} + dashboard.overview.{userId}

5.3 Practice / Assessment (MCQ)
  - MCQ questions per topic
  - Bulk submit via AssessmentAnswer::insert() — no N+1
  - Results: per-question breakdown, correct answer, explanation
  - Rate-limited: throttle:10,1 on submit
  - Hinted question IDs sent in submission (hinted_question_ids array)
    — hinted questions excluded from accuracy scoring

5.4 Code Playground (ExecutesCode trait)
  - Languages: PHP, Python, JavaScript — exec via proc_open
  - Dangerous pattern blocking (eval, exec, file ops, os module, process.env)
  - MySQL playground: separate careeros_playground DB, 4 sample tables
  - DDL blocked (CREATE/DROP/ALTER/TRUNCATE/RENAME) — would escape rollback
  - DML rolled back after each run (sample data stays fresh)
  - Rate: throttle:20,1

5.5 Coding Battleground
  - CodingProblem model with slug routing
  - Submit + view submissions
  - Rate: throttle:15,1

5.6 Dashboard
  - Cached overview: lessons %, quizzes, accuracy, learning levels passed,
    weak areas, recommendations, recent activity
  - Cache key: dashboard.overview.{userId} (5 min)
  - Busted on: lesson complete + level exam submit

5.7 Progress
  - Cached overview: learning tracks, practice by-subject, theory by-area
  - Cache key: progress.overview.{userId} (30 sec)
  - Recent activity: lessons + quiz attempts merged + sorted
  - Single SQL JOIN (no N+1), grouped in PHP

5.8 Gamification / Points System
  - user_points table: one row per user, stores current balance
  - point_events table: full audit log of every credit/debit
  - UserPoint::credit($userId, $amount, $type, $reason, $meta) — static helper
    uses DB transaction + lockForUpdate() to prevent race conditions
  - UserPoint::debit($userId, $amount, $type, $reason, $meta) — same, atomic

  Point events (implemented so far):
    quiz_correct   — +10 pts per correct answer in level exam
    quiz_perfect   — +150 pts for passing level exam (score >= 8)
    hint_used      — -50 pts per AI hint consumed

  LevelController.submitExam() awards points after scoring:
    $score * 10 per correct + 150 if passed

  HintController.unlock() deducts 50 pts before calling Ollama.

  API endpoints:
    GET  /v1/points/balance          → { balance }
    POST /v1/points/hints/{question} → { hint, new_balance } (deducts 50 pts)

6. AI / OLLAMA INTEGRATION
--------------------------------------------------------------------------------

6.1 Hint System (BUILT + WORKING)
  - Endpoint: POST /v1/points/hints/{questionId}
  - Auth: Sanctum required
  - Flow:
    1. Check user has >= 50 pts (UserPoint::debit atomically)
    2. Load question + options ($o->option_text — NOT $o->text!)
    3. Build Ollama prompt: pass correct answer in system context,
       instruct AI NOT to state it directly, ask for ONE sentence hint
    4. Call Ollama: POST http://localhost:11434/api/generate
    5. Ollama options: temperature=0, num_predict=60, num_ctx=512,
       top_k=1, repeat_penalty=1.0, stop=["\n", ".", "!"]
    6. cleanHint(): strips "Hint:" prefix, rejects if answer verbatim included
    7. fallbackHint(): extracts first keyword from correct answer for smart fallback
    8. Returns { hint, new_balance }
  - Timeout: 20s
  - Stop tokens ["\n", ".", "!"] stop at first sentence end — major speed win

  IMPORTANT BUG HISTORY: The option field is option_text on QuestionOption model.
  Using $o->text returns null → blank prompt → bad AI output. Always use option_text.

6.2 AI Explanation System (BUILT + WORKING)
  - Endpoint: GET /v1/ai/explain?question_id=X
  - Cached per question_id for 30 days (same explanation every time)
  - Rate limit: throttle:20,1
  - Returns multi-paragraph explanation in numbered format
  - Frontend: AssessmentResultPage parses AI text into structured blocks

  parseBlocks post-processing (frontend):
    - AI sometimes puts numbered section content on next line
    - Post-processing merges empty numbered blocks with next para block
    - Filters remaining empty numbered blocks
    - This prevents blank "1." / "2." sections in the UI

6.3 Production Limitation
  - OLLAMA_ENABLED=false in production (Render can't run Ollama)
  - UI gracefully hides AI features when disabled
  - Plan: move to Hetzner VPS or swap OllamaService for Groq API

6.4 Architecture Rule
  - Laravel owns: questions, correct answers, scoring, attempts, progress, DB
  - Ollama owns: explanations, hints, concept simplification
  - AI content = untrusted until validated. Never expose secrets to the model.
  - Never let missing Ollama crash the app — always check OLLAMA_ENABLED first

8. FRONTEND DATA FETCHING PATTERN
--------------------------------------------------------------------------------

All data fetching uses TanStack Query (React Query).

Standard pattern:
  const { data, isLoading, error } = useQuery({
    queryKey: ['someKey', param],
    queryFn: () => api.getSomething(param),
  })

Mutations:
  const mutation = useMutation({ mutationFn: api.postSomething })
  await mutation.mutateAsync(payload)

Points hook (usePoints.ts):
  LS_KEY = 'careeros_pts_balance'
  readCached() — reads from localStorage, returns number | null
  writeCache(balance) — writes to localStorage

  usePoints():
    initialData: readCached() ?? undefined
    initialDataUpdatedAt: 0   ← forces stale, always refetches from API
    queryFn: calls API, calls writeCache(response.balance) on success

  useUnlockHint():
    onSuccess: calls writeCache(data.new_balance)

This gives: instant display on page load (from localStorage) + silent
background refresh from API. Badge never flashes blank on reload.

14. KEY ARCHITECTURAL DECISIONS & REASONS
--------------------------------------------------------------------------------

Why two separate apps (not monolith)?
  — Independent deployability, separate scaling, cleaner separation of concerns.
  — Netlify for SPA (CDN, free), Render for Laravel (managed hosting).

Why TanStack Query (not Redux / Zustand)?
  — Server state management built in. Caching, background refetch, stale-while-
    revalidate. No boilerplate. Perfect for REST API consumption.

Why Sanctum (not Passport)?
  — SPA auth with cookies OR Bearer tokens. Simpler for this architecture.
  — Passport is overkill — OAuth server features not needed.

Why Ollama (not OpenAI)?
  — Free, runs locally, no API costs during dev, data stays local.
  — Production plan: Groq API (free tier) as drop-in replacement with same
    interface shape, or self-host on Hetzner VPS.

Why lockForUpdate() on point deduction?
  — Prevents race condition where two concurrent hint requests both pass the
    balance check before either deducts. DB-level locking is the safest fix.

Why stop tokens ["\n", ".", "!"] in Ollama?
  — One-sentence hints load 3–5x faster. Ollama can ramble without a stop.
  — Users in a timed quiz want fast answers, not paragraphs.

Why localStorage for points persistence?
  — Prevents badge flickering to blank on page reload / nav.
  — initialDataUpdatedAt: 0 in TanStack Query marks it stale immediately,
    so API refetch happens in background. Display is instant, data is fresh.

Why meta column as TEXT not JSON?
  — $table->json('meta') failed on Railway MySQL (json_object errors).
  — Fix: $table->text('meta') + 'meta' => 'array' cast in model.
  — Functionally identical — Laravel handles serialization/deserialization.

16. COMMON GOTCHAS / PITFALLS
--------------------------------------------------------------------------------

1. QuestionOption field: option_text (NOT text, NOT content)
   — Using $o->text returns null → blank Ollama prompts → garbage output

2. config() not env() in production
   — After php artisan config:cache, env() returns null
   — Always use config('services.ollama.url') etc.

3. meta column is TEXT cast as array
   — Do NOT change to json() column type — MySQL on Railway breaks
   — 'meta' => 'array' cast handles encode/decode transparently

4. Light mode CSS
   — Dark mode is default. Any color defined without [data-theme='light'] override
     WILL be invisible or broken in light mode.
   — Always add full light mode override set for new components.

5. TanStack Query initialDataUpdatedAt: 0
   — This makes initialData immediately stale, triggering background refetch.
   — Without it, cached data would prevent the API call until stale time expires.

6. Ollama stop tokens are critical
   — Without stop: ["\n", ".", "!"], Ollama generates long paragraphs.
   — With stop tokens: returns in 1–2s instead of 8–15s for hints.

7. parseBlocks in AssessmentResultPage
   — AI explanation text has empty numbered sections (content on next line).
   — Post-processing merges empty numbered blocks with the following para block.
   — Without this, users see blank "1." "2." lines in the explanation panel.

8. hinted_question_ids in assessment submit
   — Hinted questions must be sent as an array in the submit payload.
   — Backend excludes these from accuracy scoring (fair to user).

9. CSS import in PracticeSessionPage
   — Must import BOTH practice.css AND assessment.css
   — practice.css has hint button styles; assessment.css has question card styles

10. Point deduction must be atomic
    — Always use DB transaction + lockForUpdate() for debit/credit
    — Race conditions are real in concurrent HTTP requests
